## 2. 工作负载语义（G1，DESIGNED + 探针 EXECUTED）

### 2.1 Schema

```text
ScanItem {
  item_id: u32,                 // 0..N-1，稳定身份
  input_version: u32 = 1,
  input_digest: [u8;32],        // SHA256(item_id LE4 || input bytes)，由 §2.2 计算
  input_size: usize,            // 4096..=65536，步长 1024，由 (seed,item_id) 决定
  metadata_parameters: { cpu_blocks: u32, wait_us: u64 },
  workload_class: Trivial | IoWait | CpuHeavy | Mixed | LongTail,
  fault_injection_id: Option<u32>,   // None 或 Some(0x31)
  cancellation_group: u32            // 1 或 7
}

ScanResult {
  item_id: u32,
  content_digest: [u8;32],
  metadata_digest: [u8;32],
  result_class: CompletedOk | CompletedErr(u32),
  aggregation_contribution: u64
}
```

`input_size` 是派生字段：由 `generate_input(seed,item_id)` 的实际长度给出；探针结构体中的 `input_len=0` 只是模式完整性占位，不参与语义。

### 2.2 精确 REF 算法（字节级，64 位目标）

以下所有整数均为无符号、模 `2^64` 回绕；`LE4`=4 字节小端，`LE8`=8 字节小端；`SHA256` 为标准 FIPS 180-4。v0 只冻结 64 位目标（WSL2/Linux/Windows x86_64）；32 位目标的 `usize` 截断会改变块选择，标 `UNSUPPORTED_TARGET_32BIT`，不得静默运行。

```text
SplitMix64(state):
    state = (state + 0x9E3779B97F4A7C15) mod 2^64
    z = state
    z = ((z XOR (z >> 30)) * 0xBF58476D1CE4E5B9) mod 2^64
    z = ((z XOR (z >> 27)) * 0x94D049BB133111EB) mod 2^64
    return z XOR (z >> 31)

generate_input(seed, item_id):
    rng.state = seed XOR ((item_id as u64) * 0x9E3779B9 mod 2^64)
    len = 4096 + (rng.next_u64() mod 61) * 1024        // 4096..=65536
    out = byte string
    while len(out) < len:
        out.extend_LE8(rng.next_u64())
    return out[0..len]

transform(item_id, bytes, cpu_blocks):
    h = SHA256.new()
    h.update(LE4(item_id))
    h.update(LE8(bytes.len()))
    state = (item_id as u64) XOR 0x5DEECE66
    peak = 0
    n_blocks = ceil(bytes.len() / 64)
    for iter in 0..cpu_blocks:                          // iter: u32
        idx = ((state as usize) mod n_blocks) * 64
        end = min(idx + 64, bytes.len())
        window = bytes[idx..end]
        m = SHA256.new()
        m.update(LE4(iter))
        m.update(window)
        d = m.finalize()
        state = state XOR ((LE8(d[0..8]) * 0x2545F4914F6CDD1D) mod 2^64)
        peak = max(peak, state)
    h.update(LE8(state))
    h.update(LE8(peak))
    metadata_digest = h.finalize()                       // 32 bytes
    return (metadata_digest, peak)

content_digest(item_id, bytes):
    return SHA256(LE4(item_id) || bytes)                 // 32 bytes

contribution(content_digest, metadata_digest, peak):
    d = SHA256(content_digest || metadata_digest || LE8(peak))
    return LE8(d[0..8]) as u64

fold_meta(metadata_digest):
    x = LE8(metadata_digest[0..8])
    x = x XOR rotl64(LE8(metadata_digest[8..16]), 17)
    x = x XOR rotl64(LE8(metadata_digest[16..24]), 43)
    x = x XOR rotl64(LE8(metadata_digest[24..32]), 59)
    return x

aggregate(pairs):
    sorted = pairs sorted by item_id ascending
    acc = 0x5DEECE66D1CEB0BA
    for (item_id, contribution) in sorted:
        acc = acc XOR rotl64((contribution * 0x9E3779B97F4A7C15) mod 2^64,
                             item_id mod 64)
        acc = (acc + contribution) mod 2^64
    return acc
```

`REF(item)` 的权威定义：

```text
REF(seed, spec):
    bytes = generate_input(seed, spec.item_id)
    (metadata_digest, peak) = transform(spec.item_id, bytes, spec.workload_class.cpu_blocks())
    content_digest = content_digest(spec.item_id, bytes)
    contribution = contribution(content_digest, metadata_digest, peak)
    result_class = CompletedErr(spec.fault) if spec.fault is Some else CompletedOk
    return ScanResult{item_id, content_digest, metadata_digest, result_class, contribution}
```

**失败车道也必须完成全部共同工作**：fault item 照常执行 wait + transform + content_digest + contribution，然后以 `CompletedErr(0x31)` 发布；不允许因为“反正要报错”而跳过内容工作或伪造贡献。O3 会对 Ok 与 Err 两个车道的 `ResultPublished` 与 `TransformDone` payload 同时钉定。

### 2.4 四层区分

```text
SYNTHETIC_WAIT   可验证等待成本/取消切割/正确性；不可外推真实磁盘 I/O
NATIVE_IO        v0 不含；预生成 fixture/真实文件系统访问属于后续层，需单独冻结
CPU_TRANSFORM    操作计数制（cpu_blocks 次块混合 SHA256 链），不是 wall-clock 循环
FAN_IN           按 item_id 序确定性折叠，检测丢项/重复/乱序
```

### 2.5 计算量不可偷减——分层诚实声明

```text
(a) digest 层：任何仍从输入字节诚实计算的实现，跳过/缩减 CPU 工作都会改变
    metadata_digest / contribution ⇒ O3 击杀（M6 已执行证明）。
(b) 诚实规则：执行器只允许调用内容原语
    generate_input/transform/content_digest/contribution/aggregate；
    禁止调用 REF 侧入口 ref_result。
(c) 计量兜底：预注册 CPU time 下界 sanity——每单元实测 CPU time
    ≥ Σ 单项 REF 实测成本 / P（R2 执行时校验）。
(d) 原理边界：确定性合成负载下，无法仅从账本密码学证明“做过工作”；
    (b)(c) 是诚实契约 + 计量证词，不是密码学证明。如实声明。
```

### 3.1 可执行分布规则（归档补齐，纯表示细化）

审查通过的 v2/v3 已冻结每个场景的 N、工作形状、P/B 与等待档位；本归档只把“百分比/轮转”落到确定的 `item_id` 函数，使同一 `(scenario, seed, N)` 在任何平台生成同一批次。该映射不改变任何已审查的百分比、工作量或等待档位，标 `ARCHIVE_NORMALIZATION`；若 Owner 认为需要不同映射，按 §0.2 发版本化 amendment，不得静默替换。

```text
common_base5(item_id) = [IoWait, CpuHeavy, Mixed, Trivial, IoWait][item_id mod 5]

S0: class = Trivial                                  // 全部极轻
S1: class = Trivial if item_id mod 5 == 3 else IoWait
    // 4/5 IoWait + 1/5 Trivial；残差使用既有 Trivial 类，不新增类
S2: class = Trivial if item_id mod 5 == 3 else CpuHeavy
    // 4/5 CpuHeavy + 1/5 Trivial
S3: class = common_base5(item_id)                    // 4 类轮转，无 LongTail 覆盖
S5: class = common_base5(item_id)                    // 与 S3 同形状
S4: class = LongTail if item_id mod 10 == 0 else Mixed
    // 10% LongTail + 90% Mixed
S6: class = Mixed                                    // 全部混合
```

场景 CPU 工作量与等待档位**覆盖**类默认值（场景表即权威）：

```text
S0: Trivial cpu=4,   wait=0
S1: IoWait cpu=8, wait=5000us;  Trivial cpu=4, wait=0
S2: CpuHeavy cpu=2048, wait=0;  Trivial cpu=4, wait=0
S3: IoWait cpu=8, CpuHeavy cpu=2048, Mixed cpu=128, Trivial cpu=4;  全部 wait=2000us
S4: LongTail cpu=8192, wait=2000us;  Mixed cpu=128, wait=0
S5: 同 S3（IoWait 8 / CpuHeavy 2048 / Mixed 128 / Trivial 4；全部 wait=2000us）
S6: Mixed cpu=128, wait=2000us
```

注入规则：

```text
fault:  S3/S5 使用 item_id mod 16 == 13 -> CompletedErr(0x31)；其余场景无 fault
group:  全局 item_id mod 3 == 0 -> 7，否则 1
cancel: 仅 S5 在“第 164 次受理”后 request_cancel(group 7)；其余场景不发出 cancel
```

`cancel` 里程碑由 workload owner 的单线程受理计数产生，与执行器速度、完成计数、运行时长无关。速度依赖注入（完成计数达到 k、运行满 t ms）只能作为独立 stress 臂，标 `SPEED_DEPENDENT`，不得混入主表。

### 3.6 冻结补充条款

- **H3 路由**：`item_id mod K` key-affinity，`K=P`；不选 round-robin（会掏空 actor 状态所有权语义）。S4 的 LongTail 会集中于部分 actor，这是路由与偏斜的联合属性；per-actor 队列高水位单独记录，解读时标注。
- **输入物化**：确定性核心 v0 = item 执行内生成（与探针一致）；预生成 fixture 只属于 `NATIVE_IO` 层，届时单独冻结并声明 RSS 形状。
- **进程拓扑**：每轮独立进程（fresh process per round；allocator/页表状态不跨轮携带；与 O8 单批单进程一致）。
- **S0 解读**：S0 结论只关于 per-item 固定机制成本（受理+派发+terminal+join 摊销），不直接外推“扫描适用性”；S0 的 4–64KiB 输入尺寸方差记入噪声源。
- **跨场景综合规则**（预注册初值，Owner 可调）：某机制“warranted”须同时满足 ≥ 半数场景的配对区间不劣，且复杂度档不高于对照；单一场景优势不构成引入通用机制的充分证据。
- **等待档位唯一权威枚举**：S0/S2=0；S1=5ms；S3/S5=2ms；S4 仅 LongTail 尾部=2ms、其余 Mixed=0；S6=2ms。亚毫秒等待不在主表，只作 timer-granularity 校准臂。
- **计时器粒度**：H2a 的 tokio 默认 timer wheel 粒度约 1ms，会把亚毫秒等待舍入放大；主表因此只使用 ≥2ms 档位。每臂记录 `actual_elapsed / nominal_wait` 比值（诊断字段）；H2a 单元若超过先导校准阈值，延迟指标标 `TIMER_ARTIFACT` 并披露，不静默归一化。
- **K0 因子**：K0 ON/OFF 正交；K0 不见 item、不调度；`!Send` owner 不迁移；K0-ON 要求扫描会话的全部 inverse 为 total（join 不 Violated）；若 `DisposeVerdict::TeardownViolated`（kernel.rs:44-54 首个 Violated 即停），该臂记机制缺陷（无性能行），不得用 harness 代 join 补救；LIFO unwind 施加 join 逆序（注册逆序），全部 exit 仍须先于 quiescence 收据；该顺序约束属允许范围，账本可见语义不变。

# 第 2/3 部分 — 公平性、受理与生命周期

## 4. H0–H4 × K0 公平性（G1-B，DESIGNED）

### 4.1 两个预算：P 与 B

```text
P = 同时真正执行 item 工作的最大执行者数（OS 线程或 executor worker）
B = admitted-but-not-terminal 的最大计数
    B 的计数集合 = 队列 resident + 正在运行 + 已完成但尚未发布 terminal ACK
```

- `P` 是执行并行预算，不是线程总数；runtime 的辅助线程（reactor/timer/blocking pool）必须单独计入 `OS_THREADS`。
- `B` 是义务预算；队列容量、channel 容量、mailbox 容量都是**拓扑参数**，不是 B 的执行者。禁止用 `queue capacity` 代替 `B` 计数。
- 队列 resident、running、parked/waiting、effect pending、settled-not-quiescent、实际 OS 线程数必须逐臂单独记录高水位；它们不是同一个数。
- 所有 H 臂使用同一个 `B` 计数集合和同一个 `P` 上限；这是可比性的定义，不是实现细节。

### 4.2 统一受理配方（冻结；取代一切“send 成功即受理”）

对**所有** H 臂，`Admitted` 的线性化点必须是一个满足以下配方的原子段。`ItemAdmitted` 账本记录的 seq 即该线性化点的可验证序列号。

```text
ADMISSION_RECIPE(item, group):
  A. 获取 B permit
     阻塞直到 admitted_not_terminal < B（或取得等效全局 permit）。
     计数集合严格 = 队列 resident + running + completed-not-ACK。
  B. 拓扑容量处理（N1 安全裁定）
     若拓扑容量 C < B：
         在 B/取消临界区之外获取拓扑 slot（可以有界阻塞）；
         取得 slot 后重新进入取消序临界区并复验 cut。
     若拓扑容量 C >= B：
         由于在途 item 至多 B 个，机制受理动作不可能因容量阻塞，
         可在临界区内直接执行非阻塞入队/入 mailbox/spawn。
     禁止：持有 B/取消锁时等待一个已满的 H3 热点 mailbox 或 H1 channel。
  C. 取消序临界区（linearization）
     进入以取消序为权威的临界区：
       若 group 的 CancelRequested 已记录：
           立即释放 B permit（以及已取得的拓扑 slot）；
           item 保持 Offered，无 terminal 义务；返回 CUT。
       否则：
           执行机制受理动作（非阻塞入队 / mailbox insert / spawn / 等价动作）；
           追加 ItemAdmitted(batch_id, item_id, group, owner) 账本记录。
     离开临界区。
  D. B permit 释放
     在该 item 的 terminal ACK 记录之后（或同一临界区内 ACK 之后）释放；
     禁止在 ACK 之前释放。
  E. 取消里程碑
     若这是工作负载 owner 的第 k 次受理，在离开临界区后调用
     request_cancel(group)；k 由 workload owner 单线程计数，与执行器速度无关。
```

**实现安全裁定（N1，三条均为可检查断言）**：

```text
(a) 拓扑容量等待必须在原子段之外，或 C >= B 使容量永不约束。
    否则 H3 热点 actor 满箱 + 生产者持锁阻塞 + actor 无法取锁 pop = 真死锁；非法。
(b) cut 命中时必须即刻释放步 A 取得的 B permit（以及步 B 的拓扑 slot）。
    禁止 permit 泄漏使 producer 永久挂起而 O1–O10 无症状。
(c) 受理满时语义统一预注册为“阻塞”。
    拒绝式受理只允许作为显式变体臂（标 REJECTION_VARIANT），不混入主表；
    这样 S6 的“拒绝/停车率”指标跨臂同义。
```

**探针的对应实现**（`APP-C` 的 `admission_phase` / `finish_terminal`）：B 检查、cut 检查、`queue.push_back`、`pending.insert`、`admitted_not_terminal += 1` 在同一 state 锁内；队列无界，因此拓扑容量永不约束；`finish_terminal` 先追加 ACK，再递减计数并 notify。探针的 50ms `wait_timeout` 只是诊断/清理节奏，不是受理正确性的同步前提。

### 4.3 P 预算与 H2b 封顶（冻结；N2）

```text
P = 同时真正执行 item 工作的最大执行者数。

H2a（TRUE_ASYNC_WAIT）：
    runtime worker 数 = P；CPU 工作在 worker 上执行，等待期释放 worker 是同 B 下的
    合法机制属性；与 H0 的 CPU 工作做等价公平比较。

H2b（BLOCKING_OFFLOAD）：
    必须持有全局 item-execution permit（容量 P），由 scheduler 上的 item-task
    与 offload 池线程共同分摊；总执行者上界 = P。
    execution permit 的跨度 = item 执行起点 至 terminal ACK（覆盖等待相与计算相）。
    获取点 = 执行起点；释放点 = terminal ACK 处或其后。
    permit 占用高水位逐臂记录。
    禁止“仅在计算相持 permit”的形态：等待中的池线程不占 permit 会让 scheduler
    满额 CPU，2P 以合法实现回流。
    若实现不愿受此约束 => 记为独立变体臂（effective parallelism = P + pool_cap），
    标 VARIANT_2P，禁止与 H0/H1/H2a/H3/H4 同表 pooled 排名。
```

### 4.6 K0 ON/OFF 正交因子

K0 不是第六种调度器；它是组合/生命周期因子。对每个 H 臂分别跑 `K0=OFF` 与 `K0=ON`：

```text
K0=OFF：扫描会话不经过 K0 composition；机制自行创建/销毁执行者。
K0=ON ：扫描会话作为 K0 组合中的 Fiber/资源所有权关系运行；
        K0 只增加/撤销 effect 与资源所有权关系，不改变 f(item)、
        B/P 计数语义、消费者 ACK 权威或各机制的正常调度职责。
```

强制约束：

```text
1. !Send/!Sync Composition Owner 留在其控制线程；不得为跑对照把 K0 Fiber 移上 executor。
2. K0 不得参与每 block/每 item 的调度；不得成为 Scheduler/消息总线。
3. K0-ON 的 inverse 必须 total（join 不 Violated）。
   若 DisposeVerdict::TeardownViolated（kernel.rs:44-54 首个 Violated 即停）：
   该臂记机制缺陷（无性能行），不得用 harness 代 join 补救。
4. LIFO unwind 的 join 逆序是允许的；全部 exit 仍须先于 quiescence 收据。
5. K0 ON 不得改变 f(item) 或 REF；若某 H 实际无可比 K0-ON 组合：
   标 NOT_APPLICABLE 并解释，不虚构可跑组合。
```

### 4.7 禁止的不公平比较（七条可检查断言）

### 4.8 `SEMANTICALLY_INCOMPARABLE` 条件

出现以下任一情况，该臂标 `SEMANTICALLY_INCOMPARABLE`，不进入性能表，也不得用放宽协议的方式“救回”：

```text
1. 无法提供与协议等价的 settlement/quiescence：没有真实 owner terminal、
   没有可验证的 executor exit/join 边界、或收据不能作为最后记录。
2. 无法实现 Owner-death 前提（panic containment / un-polled task 的 drain owner）。
3. 无法提供可信的 effect/ACK 边界；Oracle 只能自证。
4. 运行的不是同一内容函数/REF（包括跳过 wait、缩减 CPU、改写贡献）。
5. 无法把 B 计数集合或 P 上限实现为协议定义的值。
6. 必须修改生产 Playback/K0 语义才能运行。
```

`NOT_APPLICABLE` 与 `SEMANTICALLY_INCOMPARABLE` 不同：前者是“该 H 与 K0 没有合法组合，已解释”；后者是“有组合但清偿语义不等价”。两者都不能进入 pooled 排名。

## 5. 取消 / 清偿 / 静默契约（G1-C，DESIGNED + 探针 EXECUTED）

### 5.1 生命周期状态机

```text
Offered
  │
  ├─[ADMISSION_RECIPE 线性化：ItemAdmitted]─→ Admitted
  │                                              │
  │                                              ├─[开始 item 工作]─→ Running
  │                                              │                      │
  │                                              │                      ├─→ CompletedOk
  │                                              │                      ├─→ CompletedErr(0x31)
  │                                              │                      └─[owner 观察 cancel]─→ Abandoned
  │                                              │
  │                                              └─[dequeue 前 owner 观察 cancel]─→ Abandoned
  │
  └─[cut：CancelRequested 已记录，未受理]─→ Offered（无 terminal 义务）
```

- `Running` 是语义上的义务阶段，不要求实现维护一个全局原子状态；效果序列（wait/transform/result）即在途证据。实现可以显式记录 start 时间戳，但不得用“队列空”或“Future 已创建”代替 Running/Completed。
- `Terminal` 只有三种：`CompletedOk`、`CompletedErr(code)`、`Abandoned`。每条 terminal 必须有一条 owner terminal ACK，且恰有一条。
- `Admitted` 之前的效果是非法的（O2 ghost-effect）；`Terminal` 之后的效果也是非法的（O4）。
- Offered 但从未 Admitted 的 item 在 cut 后是合法的“无义务”结果；O1 不要求每个 offered item 都有 ACK，只要求每个 admitted item 恰有一条 ACK。

### 5.2 受理线性化点与状态机不变量

```text
线性化点 = 取消序临界区内追加 ItemAdmitted 账本记录的那一刻。
一旦 ItemAdmitted 入账：
  - item 进入 Admitted，产生 terminal 义务；
  - B permit 由该 item 持有，直到 ACK 之后释放；
  - 该 item 的 group 若在之后被 cancel，owner 可以完成或 Abandon，但不能伪造结果。
若 cut 命中而未入账：
  - item 保持 Offered，无 terminal 义务；
  - 已取得的 B permit / 拓扑 slot 必须立即释放；
  - 不得追加 ItemAdmitted。
```

**重复受理禁止**：每个 Offered item 至多受理一次；O2 的 `admit_count > 1` 即 RED。受理重试不属于 v0 协议。

### 5.3 取消语义

```text
request_cancel(group):
  - 记录 CancelRequested(batch_id, group) 到账本（获得全局 seq）；
  - 切断该 group 的后续受理（此后不得再有该 group 的 ItemAdmitted）；
  - 对已经 Admitted/Running 的 item：不承诺停止、不承诺释放资源；
    它们可以由真实 owner 完成，或在 owner 观察 cancel 后 Abandon。
  - 返回时只承诺“意图已入账 + 组受理已切断”。
```

合法混合：cancel 之后，已受理 item 可以完成，也可以被 owner Abandon；两种都是合法结果。非法结果：无 cancel 的 Abandon（M4/O5）、Abandoned 之后又发布 ResultPublished（O5）、cancel 之后又受理同组 item（M7/O7）、伪造 CompletedErr/CompletedOk。

### 5.4 Terminal 权威与 Owner-death 前提

```text
CompletedOk / CompletedErr：
    owner = 完成该 item 的真实执行者（worker/task/actor/offload 线程）。
    O3 额外检查：terminal ACK 的 owner == ResultPublished 的 owner。
Abandoned：
    owner = 观察 cancel 时真实持有该 item 的执行者；
    O5 检查：该 item group 的 CancelRequested seq < Abandon ACK seq，
    且没有 ResultPublished。
Harness：
    永不写 terminal；永不替机制 join；永不根据“队列空/超时/完成计数”补 terminal。
```

**PD 前提（Owner-death premise，准入条件）**：

```text
每条 item 执行路径必须 panic-contained（catch_unwind 或等效机制），
保证 owner 存活到 terminal 发布。
H2 的 un-polled task 在 shutdown 被 Future-Drop 之前，必须由会话 drain owner
（真实机制 owner，而不是 harness）为其发布 terminal。
无法满足者 => SEMANTICALLY_INCOMPARABLE，不放宽协议、不进性能表。
```

### 5.5 三个动作必须分离

| 动作 | 显式前置 | 返回时承诺 | 不承诺 |
|---|---|---|---|
| `request_cancel(group)` | 无 | 意图已记录（账本序）+ 组受理切断 | 任何 item 已停止；资源已释放；执行者已退出 |
| `await_settlement()` | **受理阶段已结束**（offer 流关闭 / `producer_done`；第四个隐式动作显式化） | 每个已受理 item 恰有一条真实 owner terminal ACK | 执行者停止/join；聚合发布；资源回收；进程退出 |
| `await_quiescence()` | settlement | 全部登记执行者 join（exit 先于收据）；聚合 + 收据发布（收据=最后记录） | 进程退出；OS 页面回收；后续不再有进程级清理 |

- `settlement` 的等待谓词是 `producer_done && pending.is_empty()`（探针实现）；`producer_done` 置位时必须同时通知 settlement 等待者，修复 lost-wakeup。
- `quiescence` 的收据必须是账本最后一条记录；任何在收据之后追加的记录都使 O6/O10 RED。
- `request_cancel` 不得伪装成 `await_settlement`；`await_settlement` 不得伪装成 `await_quiescence`。

### 5.6 取消注入里程碑

```text
主场景里程碑 = workload owner 的单线程受理计数第 k 次（S5: k=164, group 7）。
前提：受理动作由 workload owner 单线程串行执行。
      探针 producer 即此形态；H1–H4 的受理由会话 owner 执行。
多受理者形态需要先把里程碑改为“账本序定义”，属协议变更，需 Owner 批准。
速度依赖注入（完成计数、运行时长）只作独立 stress 臂，标 SPEED_DEPENDENT；
竞态臂记录 Race Witness，未触发即 PREMISE_NOT_OBSERVED，不写 PASS。
```

### 5.7 聚合发布

```text
每批恰一条 AggregatePublished（流式部分聚合不属于 v0 协议）。
无取消：aggregate = REF 全集按 item_id 序折叠。
有取消：aggregate = 对账本中“已 terminal 且非 Abandoned、且恰有一条
        ResultPublished”的 item，按 item_id 序折叠；每个 payload 仍由 O3 逐项
        REF 钉定。Abandoned 项不计入聚合。
AggregatePublished 必须在所有 admitted item 的 terminal ACK 之后（O9）。
```

### 5.8 Quiescence 与收据

```text
QuiescenceReceipt 由会话 shutdown owner 在以下条件全部满足后追加：
  1. 聚合已发布；
  2. 每个 ExecutorSpawned 都有 ExecutorExited，且 exit seq < receipt seq；
  3. 没有未清偿的 item terminal（settlement 已完成）；
  4. 收据是账本最后一条记录。
名册完备性：任何可能追加 item 效果的 OS 线程都必须登记 ExecutorSpawned；
Linux 诊断 witness：quiescence 后 /proc/self/task 线程数 == 会话前基线
（诊断级，不是裁定级）。
```

### 5.9 合法/非法结果清单

合法：

```text
- 已受理 item → CompletedOk / CompletedErr(0x31)（内容与 REF 一致）
- cancel 后已受理 item → 完成或 Abandoned（owner 权威、无伪造）
- cancel 后未受理 item → 保持 Offered（无 terminal 义务）
- Abandon ACK 之前的 IoWaitDone/TransformDone（等待不可即时中断）
- 每批恰一条聚合、恰一条收据
```

非法：

```text
- 已受理 item 无 terminal / 多条 terminal
- terminal 无受理（幽灵 ACK）
- 重复受理
- 无 cancel 的 Abandoned / Abandoned 后 ResultPublished
- cancel 后同组再次受理
- terminal 后同 item 新效果（O4）
- 收据后任何记录（O10）
- 内容/失败车道伪造（O3）
- 聚合早于全部 admitted terminal（O9）
- 跨批次记录污染（O8）
```

# 第 3/3 部分 — Oracle、负控制与测量预注册

## 6. 独立 Oracle 与负控制（G2，EXECUTED / REPORTED_EXECUTED）

### 6.1 双账本与序列化边界

```text
RAW_EFFECT_LOG        在真实效果边界由发生线程同步追加；不是“我已经做完”的自报。
OWNER_TERMINAL_ACK_LOG 每个 item 的真实 terminal owner 追加的 ACK；外加全局收据。

两条日志共享同一个账本互斥锁；每次追加分配一个全局递增 seq。
seq 是唯一的跨线程序列化边界；所有因果判断只用 seq，不用 wall-clock、
不用队列空、不用超时、不用 sleep、不用完成计数。
```

记录 schema（与 `APP-A` 的 `LedgerRecord` 一致）：

```text
LedgerRecord {
  seq: u64,                 // 账本互斥锁内分配，从 1 开始
  log: Effect | OwnerAck,
  batch_id: u64,
  item_id: Option<u32>,     // executor 级记录为 None
  kind: EffectKind,
  payload: u64,             // 内容摘要折叠 / group id / executor id
  terminal: Option<TerminalKind>,
  owner: u64                // 追加者身份（executor id 或 coordinator id）
}

EffectKind = ItemAdmitted | IoWaitDone | TransformDone | ResultPublished |
             AggregatePublished | CancelRequested | ExecutorSpawned |
             ExecutorExited | QuiescenceReceipt
TerminalKind = CompletedOk | CompletedErr(u32) | Abandoned
```

记录纪律：

- `ItemAdmitted` 是受理线性化点；`payload` = group id，`owner` = 受理者 id。
- `IoWaitDone` 的 `payload` = 名义 `wait_us`；只有 `wait_us>0` 的非 Abandoned item 才应有恰好一条。
- `TransformDone` 的 `payload` = `fold_meta(REF.metadata_digest)`。
- `ResultPublished`（Effect log）的 `payload` = REF `aggregation_contribution`；`owner` = 发布者。
- `OwnerAck` 记录的 `kind` 固定为 `ResultPublished`（镜像结果发布），`terminal` 携带终态，`payload` = 结果贡献（Abandoned 为 0），`owner` = 真实 terminal owner。
- `CancelRequested` 的 `payload` = group id，`item_id=None`。
- `ExecutorSpawned/Exited` 的 `payload` = executor id；exit 必须登记在真实生命周期边界。
- `QuiescenceReceipt` 必须是最后一条记录。

### 6.2 O1–O10 完整谓词

记号：`i` 为 item_id；`A(i)`=ItemAdmitted seq 集合；`W(i)`=IoWaitDone `(seq,payload)` 集合；`T(i)`=TransformDone 集合；`R(i)`=Effect-log ResultPublished `(seq,payload,owner)` 集合；`K(i)`=OwnerAck `(seq,terminal,payload,owner)` 集合；`C(g)`=group g 的第一条 CancelRequested seq；`S`=ExecutorSpawned `(seq,e)` 集合；`X(e)`=executor e 的第一条 ExecutorExited seq；`Q`=QuiescenceReceipt seq；`G`=AggregatePublished `(seq,payload)` 集合；`offered`=BatchSpec 的 item_id 集合。

```text
O1_terminal_coverage
  (a) ∀i: A(i) ≠ ∅ ⇒ |K(i)| = 1
  (b) ∀i: K(i) ≠ ∅ ⇒ A(i) ≠ ∅
  (c) ∀i: |K(i)| ≤ 1
  (d) ∀i with any record: i ∈ offered
  说明：offered 但从未 Admitted 的 item 允许没有 ACK（cut 后的合法无义务结果）。
  违反签名：admitted-but-no-terminal / terminal-without-admission /
            duplicate-terminal / ghost-items-not-offered。

O2_exactly_once_effects
  (a) ∀i: |A(i)| ≤ 1                                     // 重复受理禁止
  (b) ∀i: A(i)=∅ ∧ (W(i)∪T(i)∪R(i) ≠ ∅) ⇒ RED            // 幽灵工作
  (c) 令 K(i)={唯一 ACK}；若无 ACK，跳过（已由 O1 判红）
  (d) 若 terminal ≠ Abandoned：
        expected_wait = 1 if wait_us(i)>0 else 0
        |W(i)| = expected_wait
        若 expected_wait=1：W(i) 唯一 payload = wait_us(i)
        |T(i)| = 1
        |R(i)| = 1
  (e) 若 terminal = Abandoned：
        |W(i)| ≤ 1；不要求 T/R 数量（O4/O5 另行裁定）
  说明：wait 的数量与 payload 双裁定；跳过/缩短等待被 M8 击杀。

O3_content_vs_ref
  对每个 offered i 且 |K(i)|=1（否则 O1 territory）：
  (a) 若 terminal ≠ Abandoned 且 R(i) ≠ ∅：
        first(R(i)).owner = first(K(i)).owner               // ACK owner 一致性
  (b) 若 terminal = CompletedOk：
        REF(seed,i).result_class = CompletedOk
        first(R(i)).payload = REF.aggregation_contribution
        first(T(i)).payload = fold_meta(REF.metadata_digest)
  (c) 若 terminal = CompletedErr(code)：
        REF(seed,i).result_class = CompletedErr(code)
        first(R(i)).payload = REF.aggregation_contribution   // Err 车道同样钉定
        first(T(i)).payload = fold_meta(REF.metadata_digest)
  (d) 若 terminal = Abandoned：R(i) = ∅
  (e) 聚合：
        若账本中无任何 CancelRequested：
          expected = aggregate([(i, REF(seed,i).contribution) for i∈offered])
        否则：
          expected = aggregate([(i, first(R(i)).payload)
                      for i with |K(i)|=1, terminal≠Abandoned, |R(i)|=1])
        G 必须非空；∀g∈G: g.payload = expected
  说明：cancel 臂的成员集合是调度相关的（in-flight 可完成或 Abandon），
        但每个成员值仍由 REF 钉定；丢项/重复/顺序错误仍被检出。

O4_no_effect_after_item_terminal
  ∀i with first ACK seq a：
    不存在 e ∈ W(i)∪T(i)∪R(i) 使 e.seq > a
  说明：这是逐 item 边界，不是“全局 quiet 后没有 effect”；M3 击杀。

O5_abandon_legitimacy
  ∀i with |K(i)|=1 且 terminal=Abandoned：
    C(group(i)) 存在 且 C(group(i)) < first(K(i)).seq
    R(i) = ∅
  说明：无 cancel 的 Abandoned、cancel 记录晚于 ACK、Abandoned 后有结果，均 RED；
        M4 击杀。Abandoned 的 owner 是荣誉锚定（无前序 effect 可比对），
        O5 只能验证“cancel 先于 ACK + 无结果”；如实声明。

O6_executors_joined_before_quiescence
  (a) Q 存在
  (b) ∀(spawn_seq,e)∈S：X(e) 存在 且 X(e) < Q
  (c) 账本最后一条记录的 kind = QuiescenceReceipt
  说明：名册完备性（任何可能追加 item 效果的线程都登记 ExecutorSpawned）
        是代码审查/可检查断言，不是 O6 自动证明；M5 击杀 exit-after-receipt。

O7_no_admission_after_cancel
  ∀i∈offered with A(i)≠∅：
    若 C(group(i)) 存在，则 min(A(i)) < C(group(i))
  说明：只检查首次受理 seq；重复受理由 O2 裁定。M7 击杀 cancel 后受理。
        单受理者 + 取消序临界区是该检查的结构前提。

O8_batch_isolation
  ∀record r：r.batch_id = spec.batch_id
  说明：探针一轮一进程、单批；任何 foreign batch id 即污染。
        跨批突变未执行（O8 在当前 harness 下是 DESIGNED-only 判别力）。

O9_fanin_after_all_terminals
  ∀a∈G with a.batch_id = spec.batch_id：
    ∀i with A(i)≠∅：|K(i)|=1 且 first(K(i)).seq < a.seq
  说明：never-admitted 的 item 没有 terminal 义务；M1 连带击杀（聚合早于缺失 terminal）。

O10_no_effect_after_quiescence
  Q 存在；不存在 r.seq > Q 的记录
  说明：全局收据后的任何记录（包括清理阶段的 ExecutorExited）都 RED；
        M5 击杀；O6 的 exit-after-receipt 是同一边界的另一面。
```

## 7. 测量预注册（G3，DESIGNED / NOT_RUN）

### 7.1 九个计时段

所有时间戳由 harness 在真实事件边界记录；`seq` 只用于因果，不用于时长。九段独立记账，允许部分区间重叠；报告必须同时给出区间定义，禁止只报一个“总时间”。

| # | 计时段 | 起点 | 终点 | 说明 |
|---|---|---|---|---|
| P1 | `INITIALIZATION` | 进程进入 `main` 前由 harness 打的 `t_process_start` | 机制就绪（runtime/线程池/actor 创建完成；K0 ON 时 composition settle 完成） | 含动态加载/运行时启动；K0 ON 的 compose/settle 计入 |
| P2 | `FIXTURE_LOADING` | 机制就绪 | fixture 就绪 | v0 确定性核心在 item 内生成，故为 0；NATIVE_IO 层另冻结 |
| P3 | `WARMUP` | warmup 轮首次 offer | warmup 轮 quiescence | 3 个独立 seed（31–33），弃置；不进正式统计 |
| P4 | `ADMISSION` | 首次 offer | offer 流关闭（`producer_done`） | 含 B permit 等待；S5 的 cancel 可能发生在此区间内，单列 CANCELLATION 子区间 |
| P5 | `STEADY_EXECUTION` | offer 流关闭 | settlement 返回 | 无取消场景的执行尾巴；取消场景含 post-cancel drain；与 SETTLEMENT 可重叠 |
| P6 | `CANCELLATION` | 调用 `request_cancel` | CancelRequested 入账 + 最后一笔该组受理切断 | 子区间，不从未重叠区间中扣除；无取消场景为 0 |
| P7 | `SETTLEMENT` | cancel 记录（无取消则为 offer 关闭） | `await_settlement` 返回 | 所有 admitted item 恰一条 terminal ACK |
| P8 | `QUIESCENCE` | settlement 返回 | `await_quiescence` 返回（全部 exit + 聚合 + 收据） | 收据必须是最后记录 |
| P9 | `FINAL_TEARDOWN` | quiescence 返回 | 进程退出 | 含 drop/free/OS 清理；不用于机制排名主指标 |

**WITH/EXCLUDE STARTUP 双报告（同时冻结，不按倾向选一个）**：

```text
WITH_STARTUP    = t_quiescence - t_process_start（或 t_process_exit，二者都报）
EXCLUDE_STARTUP = t_quiescence - t_first_offer
STARTUP_COMPONENT = INITIALIZATION + FIXTURE_LOADING
WARMUP 不计入任何正式轮；warmup 仅用于热机，单独报告其区间。
```

### 7.3 统计方案

```text
轮次与配对：
  30 个主种子 = 30 个配对轮；同一 seed 下所有 arm 配对比较。
  每个 arm 先跑 3 个 warmup 轮（seed 31–33），独立进程，弃置。

  对每个 seed，arm 顺序 = 按
    SHA256(LE8(seed) || 0x00 || ASCII(arm_id))
  的前 8 字节按小端解释为 u64，升序排列。
  arm_id 必须唯一且稳定（如 H0-OFF、H1-OFF、H2a-OFF、H2b-OFF、H3-OFF、H4-OFF，
  K0-ON 同理）。该规则是确定性的、可复现的；不改变“随机化+配对”的语义。

先导阶段（MDE）：
  在 native Linux 上用小样本先导估计配对差 SD 与仪器开销差；
  由 SD 推导 30 轮的 MDE。
  SESOI（预期效应量）必须在先导数据产生之前书面预注册；

  若 MDE > SESOI：上调轮数后再冻结正式方案；不得“看到赢家就停”。

不确定区间：
  95% CI；主分析 = 轮级配对差值。
  分位 CI = 按轮 block bootstrap（重采样轮 → 池化 → 算分位 → 重复）；
  另报每轮 p99 分布与 p99 有效样本量。
  池化分位不得忽略轮内相关。

异常值：
  MAD > 6 标记并披露；只有诊断出的环境事件可以剔除，且必须保留原始记录。
  不得因为“看起来是赢家/输家”而剔除。

停止规则：
  固定 30 轮；禁止可选停止。
  INVALID 轮允许重跑，上限 2 次；同 seed 新轮号留痕；仍失败则该单元
  ENV_FAILED，剔除并披露。
  不得因结果显著性提前停止或延长。

  loadavg(5min) > 0.5 × P_phys
```

### 8.2 迁移边界（问题 4 的预答）


### 8.3 可迁移性等级

```text
S0/S1/S3 的等待/唤醒结论：只可迁移到“非实时、可阻塞/可 async”的第二类负载。
S2/S6 的 CPU/背压结论：只可迁移到“有明确 B 预算”的批处理负载。
S4 的偏斜/stealing 结论：只可迁移到“item 成本高度不均且可分割”的负载。
H2a 的 timer 结论：受 timer 粒度限制，不能迁移到亚毫秒等待。
H2b 的 offload 结论：只适用于“允许阻塞线程池”的宿主。
K0 ON/OFF：只说明组合/生命周期成本，不说明调度优劣。
```
